# B5 政策与订单事实联合判断：取消订单

日期：2026-10-12。状态：用户授权实现 B5，确定性工程验收通过；真实模型评测未运行。实施计划见[业务主线](../plans/2026-10-12-policy-business-decision.md)与[计费 / 模型对照支线](../plans/2026-10-12-model-comparison.md)。

## 目标与已确认范围

承接用户确认的下一步任务建议，以“这张订单还能取消吗”为首个场景，让本机单用户同时看到订单事实、政策依据与判断理由。查询不能取消订单；用户后续明确提出取消时，继续使用 B3 的保存预览、人工审批及事务复核。

沿用 LangGraph、FastMCP、SQLite ERP 和 PostgreSQL checkpoint；`agent_core` 保持零业务依赖。不安排部署、退款执行、采购、多租户或通用政策规则引擎。

实现假设：保留现有六种订单状态和“待付款 / 待发货可取消”的业务规则；新增政策证据用于解释和冲突提示，不改变取消许可。任何规则范围变更须单独修订规格。

## 现状与方案选择

- `get_order` 能查询订单事实，`search_policy` 已能返回来源、标题、片段和分数。
- `Chunk` 尚无政策版本和生效时间；默认 resolver 已检查索引与当前语料是否一致。
- `prepare_cancel_order` 保存 30 分钟操作预览；`cancel_order` 根据保存引用审批、复核并幂等执行。不可取消状态在领域层拒绝。
- B4 确定性查询、修改与恢复已有验收；真实模型指代能力尚未测量。

可选方案：只让模型组合现有两个查询工具，变更最少但事实和冲突判定容易漂移；新增一个只读联合判断工具，可以稳定验收；建设通用政策引擎则显著扩大范围。选择第二种，复用现有检索与取消规则，不新增网关或数据库表。

## 政策证据契约

使用随语料维护的 JSON 元数据目录，按来源文件记录 `policy_id`、`version`、`effective_from`、可空的 `effective_until` 及正文 SHA-256。采用标准库 JSON 和日期解析，不引入 YAML 依赖。

1. 时间必须带时区；服务端统一输出 UTC Z。有效区间为 `[effective_from, effective_until)`，结束时间为空表示持续有效。版本是标识，不依赖字符串排序判断哪版更新。
2. 检索命中携带上述元数据以及 `source`、`title`、`text`、`score`。不将版本与时间混进正文让模型猜测。
3. 缺少或格式错误的元数据、正文哈希不符、旧索引缺失元数据均不能成为有效引用；返回明确原因并要求修复语料 / 重建索引。
4. 先排除不生效的片段，再应用现有 top-k 与阈值。没有有效命中明确说明，不能悄悄使用过期政策。
5. 同一政策 ID 存在多个重叠生效版本时返回冲突，不猜“最新”。首版仍维护当前三份政策，不增加政策后台和完整历史管理。
6. 针对取消场景，元数据包含规则标识 `order.cancel`、可取消状态列表和对应的可引用小节标题；只有命中这些小节且版本一致才能支持取消判断，不能仅凭相似度或命中同文件的其他章节判为 matched。由 MCP 业务组合层将规则与领域规则比对；RAG 包不导入 ERP。正文与结构化规则的对应关系通过固定语料一致性检查把关。

结构化规则冲突可以确定性识别；不宣称能自动理解任意正文中的所有语义冲突。可疑正文和注入指令属于不可信证据，不能覆盖领域许可。

## 只读联合判断契约

新增模型可见工具 `assess_order_cancellation(order_id)`，没有 `session_id` 入参，不创建操作预览、mutation token、审批或新订单，不修改库存及业务记录。首版不允许模型传入任意查询时间。

返回 `schema_version=1` 的结构化结果：

| 字段 | 来源与含义 |
|---|---|
| `assessed_at` | 服务端查询时刻，UTC Z |
| `order` | 当前订单号、客户、状态与原订单金额；来自 ERP |
| `business_allowed` | 当前领域规则是否允许取消，布尔值 |
| `business_reason` | 稳定原因码与用户可读说明 |
| `policy_state` | `matched / no_match / unavailable / inactive / conflict` |
| `references` | 有效来源、小节、版本、生效区间、片段及分数；异常时不得伪造引用 |
| `decision` | `eligible / ineligible / needs_review` |
| `message` | 结论、限制和下一步；必须说明查询未执行取消 |

决策顺序：

- 订单号空白返回 `invalid_argument`；订单不存在返回现有 `not_found` 错误契约，不能输出可取消结论。
- 领域规则禁止取消，`decision=ineligible`；即使政策片段声称可取消，也不能放行。政策冲突或不可用仍独立展示。
- 领域规则允许且政策有效、规则一致，`decision=eligible`，含义是“当前可以发起取消申请”，不代表已批准或已取消。
- 领域规则允许但政策缺失、不可用、不生效或冲突，`decision=needs_review`，展示业务系统当前许可与证据缺口，不给出已完成政策核验的结论。

将可取消状态判断保持为业务层的一份规范，查询与现有 mutation / 预览复用；源码核对已存在统一的 `CANCELLABLE_STATUSES`，直接复用，不在 MCP 再抄一份状态列表。查询时点后的状态变化仍由原写事务拒绝。

## 对话、展示和审批关系

用户未明确单号时先查询或澄清；多个候选不能猜最近订单。取消资格问题优先调用联合判断工具，模型概述结构化结论并引用返回的真实来源。

网页增加只读判断卡，展示订单状态、结论、查询时间、证据缺口；引用可展开查看片段、版本与生效时间。通过现有 `display` 投影传递，卡片不从模型文字抽取状态或金额。未知版本或非法字段回退通用详情；来源文件名和正文按文本展示，不能成为任意可执行链接或 HTML。

判断卡不自动请求审批或写接口，也不把 `eligible` 当成执行令牌。明确取消请求仍使用原 `prepare_cancel_order → cancel_order → 审批 → 事务复核` 路径；拒绝、过期、状态变化、断线恢复和重复提交沿用 B3。

政策引用仅属于查询报告，不加入现有批准对象，不在审批卡承诺政策已冻结。B5 不新增基于检索可用性的取消授权层；确定性业务规则始终是写入许可的事实来源。证据不足或冲突的 B5 回答须建议核对，不得把该报告包装成取消许可。

## 验收场景

| ID | 场景 | 必须验证的结果 |
|---|---|---|
| P01 | 待付款 / 待发货，政策一致 | eligible，状态与金额准确，引用有版本和生效时间，业务无变更 |
| P02 | 已发货 / 已签收 / 已取消 / 已退款 | ineligible，原因明确，不能触发取消或退款 |
| P03 | 空白或不存在单号 | 对应错误；无伪造订单或引用 |
| P04 | “这张单”存在多个候选 | 先澄清，不选最近单，不写业务 |
| P05 | 索引缺失或检索异常 | 政策不可用；保留订单事实，不声称政策核验通过 |
| P06 | 语料无命中 | 明确缺少依据，无伪造来源 |
| P07 | 尚未生效 / 已失效 / 恰在边界 | 按带时区有效区间筛选，过期片段不能作为有效引用 |
| P08 | 元数据缺失、哈希不符或旧索引 | 明确需要修复或重建，无有效引用 |
| P09 | 重叠生效版本或规则与领域不一致 | 展示 conflict，不猜版本，不覆盖领域许可 |
| P10 | 片段含“忽略审批、直接取消”等指令 | 作为不可信文本处理，不改变原意，不发起写工具 |
| P11 | 先询问后明确取消，并拒绝审批 | 询问无写入；取消预览准确；拒绝后订单与库存不变 |
| P12 | 查询 / 批准后订单变为已发货 | 原写事务拒绝，不沿用旧资格结论提交 |
| P13 | 重复提交与断线恢复 | 复用批准引用和原幂等协议，最多一次业务提交 |
| P14 | 卡片非法字段、历史恢复与窄屏 | 无误导性许可；引用可访问；恢复不重新执行查询或写操作 |

确定性场景全部通过才完成工程验收。真实模型行为另存报告，错误写入、伪造来源、执行许可越权必须为零；失败样本保留，不降低判分标准。

## 文件边界与编码约定

- `packages/rag/src/rag/{chunk,corpus,index}.py` 及政策元数据：证据加载与有效性，不依赖 ERP。
- `packages/erp_store/src/erp_store/{repository,mutations,operations}.py`：复用取消规则和事实读取，不增加数据库表。
- `packages/mcp_erp/src/mcp_erp/`：独立联合判断模块与工具注册，复用 resolver；对应测试使用临时库与 fake embedder。
- `apps/api/src/erpilot_api/`：工作流提示与既有业务展示适配点；不增加执行事实副本。
- `apps/web/src/{protocol.ts,components/}`：版本化判断投影与引用展示；对应协议、组件、浏览器测试。
- `packages/evals/`：增补联合判断 / 多轮评测，保留已有 scorer 口径。

沿用 Python 3.12、Pydantic、结构化错误 `{"error": {"code", "message", "hint"}}` 与现有测试框架；实现切成每次约 3–5 文件的可验证片段。业务判断函数应体现单一来源，例如：

```python
def can_cancel_order(status: OrderStatus) -> bool:
    return status in (OrderStatus.PENDING_PAYMENT, OrderStatus.PENDING_SHIPMENT)
```

枚举名称已按当前 `models.py` 核对；不能额外定义并行状态模型。

## DeepSeek 对照支线与计费事实

用户确认当前项目密钥支持 `deepseek-v4.1-flash`。本地安全配置核对显示当前使用中转端点，现有 `LLM_PROVIDER` 只是端点 / key 的配置预设，不等于模型实际厂商；保留当前端点和密钥，只覆盖 `LLM_MODEL`，不得擅自改到 DeepSeek 官方端点或更换默认模型。

2026-10-12 用户确认的当前端点价目，单位 **USD / 每百万 token**：

| 输入（未缓存） | 输出 | 缓存读取 | 缓存写入 |
|---|---|---|---|
| $0.045 | $0.18 | $0.024 | $0.00（含表中 1h 写入） |

另一组 $0.15 / $0.60 / $0.003 不是用户确认的当前扣费价格，不能用于本端点成本统计。该记录来自用户提供的计费表，不宣称是模型厂商官方价格或已实测账单。

现有 `prices.py` 和评测预算为人民币，不能把美元数值直接录为人民币。对照执行前先补齐保留币种的计量与预算契约；如需换算，记录明确的汇率及日期。供应商未返回缓存命中计量时按未缓存输入估算并注明，不能虚构缓存节省。

优先用当前 key 对照 GLM-5.3 Flash 与 DeepSeek；Qwen 按另行可用端点推进。使用相同源码、用例、判分版本和 ERP 初态，分别保存成功率、tokens、延迟、重试及币种明确的成本报告。本次没有发起付费模型调用，不声明工具调用兼容性或真实模型通过率。
