# Erpilot 功能深化里程碑与后续路径

更新：2026-10-11。用户已确认本路径并要求开始开发；本阶段不安排部署。

## 目标与边界

把查询、建议、审批、执行连接为可验证的业务流程，继续服务于「会请示的 ERP 智能体」作品集定位。优先完成报价建单闭环，再深入任务状态和政策依据；以验收结果推进，不承诺固定发布日期。

维持本机可信单用户范围、现有 LangGraph / MCP / SQLite / PostgreSQL checkpoint 架构及 `agent_core` 零业务依赖。不扩展完整 ERP、支付网关、多租户、多 agent 编排或自动采购。

## 里程碑

| 阶段 | 用户可见结果 | 核心验收 | 依赖与状态 |
|---|---|---|---|
| B1 计价一致 | 相同商品、数量、现价下，报价与新订单金额一致 | 10/50/200 档位边界、同 SKU 合并、不跨 SKU 累计、金额舍入、原单重放与历史快照 | 2026-10-11 完成；[验收记录](../reports/acceptance/2026-10-11-pricing-consistency.md) |
| B2 订单草稿与确认闭环 | 多商品草稿可修改；用户能按确定的明细和金额批准建单 | 草稿版本与审批绑定；修改使旧批准失效；执行时复核价格、可售状态和库存；重复提交只建一单 | 已实现，验收记录见 [B2 报告](../reports/acceptance/2026-10-11-order-draft.md) |
| B3 业务审批体验 | 建单、取消、库存调整均有业务摘要和变更影响 | 金额、商品、库存变化取自后端事实；拒绝明确未执行；失效操作重新确认；断线后恢复同一批准对象 | 与 B2 共用批准对象，B2 后逐工具扩展 |
| B4 多轮任务与历史会话 | 「把第二个改成 50 件」可准确修改当前草稿，旧任务可找回 | 客户、商品、数量和约束保存在结构化状态；歧义先澄清；上下文裁剪不丢草稿；重启恢复；会话间隔离 | B2–B3 验收后实施 |
| B5 政策与业务联合判断 | 「这张订单还能取消吗」同时给出订单事实、政策依据和可执行结果 | 政策版本/生效时间与可展开引用；冲突和证据不足明确说明；确定性业务规则掌握执行许可；间接注入不得越权 | B3 后可独立开展 |
| B6 有依据的补货建议 | 结合销量和库存生成可审阅的补货清单 | 统计窗口和有效订单口径明确；展示库存、销量、预计可售天数；缺少采购周期说明假设；零销量和异常数据不伪造结论 | B4–B5 后评估，只读建议 |

## B1 的明确计价契约

1. 先合并同一 SKU 数量，再按该 SKU 的总数量命中折扣；不同 SKU 不累加。
2. 数量 10/50/200 件起分别为 98 折、95 折、9 折，低于 10 件无折扣。
3. 以十进制计算折后单价，按四舍五入（ROUND_HALF_UP）保留两位；行金额 = 已舍入单价 × 数量；订单金额 = 各行金额之和，保留两位。
4. 新订单保存下单时的折后成交单价，历史订单不重新计价；幂等重放返回原提交结果，不采用新现价。
5. B1 不承诺冻结旧报价。当前报价是参考；执行时按现价计价。B2 才引入批准版本与价格变化复核。
6. 保持现有 API 金额数值字段、数据库结构和历史订单汇总算法；报价及新单成交单价使用十进制计算，不宣称完成全库金额类型迁移。折后单价舍入为零时报价和建单均返回业务错误，避免零价单。

## 后续实施顺序

B1 已完成计价一致；B2 已接通会话草稿、可编辑明细、版本审批和原子提交。草稿有效期 30 分钟；条件变化产生失效结果，刷新后须重新审批。模型提出操作，业务层计算与校验，审批层决定是否执行。接下来推进 B3 的取消与库存调整摘要，再按验收结果进入 B4。

B3 先覆盖建单，复用 B2 明细；再扩展取消和库存调整，不同时重写所有审批工具。B4 用真实多轮需求和结构化草稿检验状态设计，再增加历史列表。B5 以取消订单这一单场景检验政策和事实结合，达标后扩展退换货判断。B6 首先输出建议，不新增采购写能力。

## 贯穿各阶段的验证

- 每个里程碑提交一份独立设计与实施清单，记录完成部分、未完成部分及验收入口。
- 单测与集成测试使用临时业务库及脚本化模型；真实模型结果另存报告，不合并为确定性通过率。
- 业务状态验证覆盖修改数量、拒绝后重提、价格/库存变化、断线恢复、重复提交与跨会话隔离。
- 继续使用现有评测判分标准，不为了新功能通过而放宽失败判定。
- 跨 GLM / DeepSeek / Qwen 的真实对比作为已有能力验收支线，独立于 B1–B6；未运行前不写对比结论。
