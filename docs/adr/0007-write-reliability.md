# ADR-0007：SQLite 事务幂等与审批清理

日期：2026-10-05；状态：已实施。范围仍为单主管 agent、20 个工具和本机单用户展示。

## 问题

写操作提交后丢失响应会被执行层重试；库存读改写和订单序号分配在并发连接下
可能竞争。审批 future 只登记不清理会遗留 waiter，SSE 取消还可能在 cleanup
之前再次取消异步清理。原评测只看工具名与文本，无法证明批准确实执行。

## 决定

1. 四种 mutation 共用 `mutation_requests` 表，以 `client_token` 为主键，保存
   工具名、规范化参数与成功结果。建单合并并排序 SKU、清理客户名前后空格。
   查重、业务更新与结果记账在同一事务；重放返回首次提交结果，同键异参拒绝。
2. SQLite 在读取业务数据前 `BEGIN IMMEDIATE`，用数据库文件写锁保护库存与
   订单序号分配。旧库第一次写入时按需创建幂等表，无需重新 seed。
   使用 NullPool，Session 结束后释放实际连接，避免 Windows 临时库删除失败。
3. Tool 只有显式 `retry_safe` 才允许写操作重试；MCP bridge 生成并复用同次执行
   的 token。含写工具的整轮模型任务不自动重跑，避免模型重新生成另一笔写入。
4. 审批结束即删除 waiter；取消与生成器关闭由 loop 同步清理已完成挂起任务，
   未完成任务注册结束回调后取消。cleanup 在可取消的 await 之前执行，覆盖
   AnyIO 的持续取消。API / trace / service 显式关闭下层流。
5. 评测保留工具参数、返回值与 ok，批准要求成功执行证据与准确业务状态；
   拒绝要求四张业务表不变。每条写 case 独立 seed 临时库，报告逐条 checkpoint。

## 代价与边界

SQLite 写入串行化适合当前 demo，30 秒锁等待后可以失败，不能替代生产容量
评估。PostgreSQL 迁移须重新设计行锁、唯一约束与订单编号，不是只换 URL。
幂等记录尚无清理策略；不保存失败结果；无 token 的直接 mutation 调用不保证
重放，新模型调用也不保证语义层去重。批准且已开始的写事务可能在断连后完成，
本轮前会话历史回退不能撤销已经提交的业务操作。

审批与会话仍在内存中；本 ADR 不实现重启恢复、审批归属或身份认证。下一阶段
持久化任务、审批与写入 token，并定义“提交完成但回答未完成”的恢复语义。

## 证据

测试覆盖重启重放、异参冲突、同键并发、库存增减竞争、并发建单不超卖、
提交后响应丢失、拒绝零业务变更、并行审批关闭与 AnyIO 断连取消。
四场景离线演示保留真实业务状态与 trace，脚本化模型不计入模型成功率。
