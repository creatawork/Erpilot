# AI 回答渲染与实时工作反馈：两阶段落地方案

日期：2026-10-07

状态：阶段一、阶段二已完成；审查发现的 6 项问题已修复并通过回归验证。
范围：Erpilot React 前端、Agent 流式事件、API 展示投影与会话恢复。

进度记录：用户已确认阶段一完成。本次仅更新文档状态，未重新执行代码审查、测试或浏览器验收；下述阶段一内容保留为设计与验收基准，不作为本次独立验证的结果。

## 1. 目标与约束

用户希望解决两个问题：AI 回答中的 Markdown 没有正确排版；AI 分析请求、生成工具调用、执行工具时缺少明显反馈，难以判断任务是否仍在运行。

成功标准：发送后立即看到当前状态；工作阶段由真实事件更新；最终回答可读；刷新后的已完成回答与工具记录保持顺序；没有思考内容时仍能知道当前在等待什么。

本方案分两阶段交付，每阶段可以独立使用：

1. Markdown 渲染、实时阶段状态、工具时间线。
2. 可选思考增量、业务结果卡片、持久化展示记录与刷新恢复。

约束：

- 复用现有 fetch + SSE、LangGraph custom stream，不另建 WebSocket 通道。
- 维持现有审批、checkpoint、幂等键与恢复语义。界面改动不能触发额外写操作。
- 只展示收到的模型内容和实际工作事件，不按计时器编造思考、任务步骤或进度百分比。
- 模型与端点不提供思考内容时，退化为阶段状态和工具反馈。
- 心跳代表连接存活，不代表模型或工具取得进展。
- 本文定义设计与验收要求，不代表代码已经具备这些能力。

## 2. 现状与问题定位

本节记录方案制定时的实现基线。阶段一完成后的实际实现以当前代码为准；进入阶段二时需核对已经落地的事件和内容模型。

| 位置 | 已有能力 | 缺口 |
| --- | --- | --- |
| `apps/web/src/App.tsx` | 消费 step、delta、工具和审批事件 | 正文直接显示字符串；阶段主要在顶部；工具名称为技术名称 |
| `apps/web/src/App.css` | 气泡、工具详情、光标 | 缺少 Markdown 排版、持续状态、阶段耗时和业务卡片样式 |
| `apps/web/src/session.ts` | Turn 保存 text 和 tools；从快照恢复 | 文本和工具分离，不能表达交错顺序；实时与恢复消息分组不同 |
| `apps/web/src/protocol.ts` | POST SSE 增量解析 | 缺少思考和执行状态事件；未知事件与数据校验需要明确策略 |
| `packages/agent_core/src/agent_core/llm.py` | stream=True；正文逐段产出 | 未读取 reasoning_content；工具调用参数收完后才产出完整 ToolCall |
| `packages/agent_core/src/agent_core/graph.py` | model 节点即时转发 TextDelta；prepare 发工具开始事件 | tool_started 表示请求已准备，不能直接等同于 handler 已开始执行 |
| `apps/api/src/erpilot_api/events.py` | AgentEvent 转 SSE | StepEnd 目前不下发；没有思考、实际执行、心跳业务事件 |
| `apps/api/src/erpilot_api/service.py` | 会话快照、审批和中断恢复 | 快照以模型 messages 与工具历史为主，没有完整展示事件记录 |

当前代码是模型到浏览器的真实正文流式链路，不是前端收到完整答案后模拟打字。长时间没有正文可能发生在模型思考和工具参数生成阶段。代理缓冲、首包延迟等需要运行时验证，不能仅从代码断定。

另一个关键点：现有工具执行结果的 `ok` 主要表示调用是否正常返回。业务错误或审批拒绝可能仍以正常返回的 JSON 表达，因此不能用 `ok=true` 单独判定业务成功。

## 3. 选择的方案与替代方案

选择“现有 SSE 增量增强 + 前端有序内容块 + 后端展示投影”。它利用已经存在的事件和恢复机制，先改善体验，再补充展示数据，不改变 Agent 编排方式。

不选择只增加 loading 动画：可以缓解空白，但无法解释审批、并行工具、失败和阶段变化。

不选择完全依赖模型生成进度说明：说明出现时机不稳定，也不能作为业务事实来源。确定性的工具状态由运行时产生，模型正文只负责解释。

不选择一次性重构通信与执行框架：当前流式通道已经可用，更换框架不能直接解决 Markdown 和缺失事件的问题。

## 4. 阶段一：回答排版与实时工作时间线

### 4.1 回答渲染

引入 `react-markdown` 与 `remark-gfm`，支持段落、加粗、列表、引用、表格、链接、代码块。正文使用常规文档排版；用户输入保留原有换行显示。

- 不启用任意原始 HTML；不使用模型文本拼接 innerHTML。
- 链接限制危险协议；新窗口链接带合适的 rel 属性。
- 表格与代码块横向滚动，移动端不撑开聊天容器。
- 流式期间按累积文本重新解析，允许尾部未闭合语法暂时按普通文本展示，收到后续片段后正常成形。
- 渲染更新按浏览器帧批量合并，避免每个微小片段都触发滚动和重排；结束、错误、审批事件及时刷新。
- 用户接近底部时跟随输出；用户向上阅读时保持位置，提供“回到最新”入口。

### 4.2 当前回答内的进度区域

发送后创建助手占位内容，立即显示“正在连接…”。收到 start 显示“请求已接收”，收到 step 显示“正在分析请求 · 第 N 轮”。轮次是模型调用次数，不称为用户任务完成进度。

状态位于当前助手回答内部，顶部仅保留简短会话状态。过程默认展开；正常完成后显示摘要并可折叠；等待审批和失败信息保持可见。

| 触发来源 | 展示状态 | 说明 |
| --- | --- | --- |
| 本地发送动作 | 正在连接 | 此时尚不能声称服务端已接收 |
| start | 请求已接收 | 连接与流已建立 |
| step | 正在分析请求 | 模型请求已开始，不表示有公开思考内容 |
| delta | 正在生成回复 | 本轮可能仍会提出工具调用，不提前称为最终回答 |
| tool_started | 已准备操作 | 已取得完整调用请求，尚不能声称实际执行 |
| approval_pending | 等待你的批准 | 审批等待不是卡住 |
| approval_resolved，批准 | 已批准，等待执行 | 等待实际执行事件 |
| approval_resolved，拒绝 | 已拒绝，未执行 | 后续正常回填也不得转为业务成功 |
| tool_executing（新增） | 正在执行操作 | handler 即将实际调用 |
| tool_finished | 操作返回结果 | 经结果分类后显示成功、失败或未执行 |
| done，completed=true | 已完成 | 收起过程，可展开查看 |
| done，completed=false | 达到执行轮次上限 | 不显示正常完成 |
| error / 非预期流结束 | 执行失败 / 连接中断 | 保留已收到内容，进入状态同步或显式恢复流程 |

耗时从本地阶段开始计时，仅作为本次连接的等待时长。无事件时计时持续更新，不产生新工作节点。审批耗时与执行耗时分开显示。

工具标题通过已知工具名称映射为“查询库存”“调整库存”“创建订单”等。根据已验证的参数展示简短摘要，例如“A1001 · +9 件”。未知工具回退到名称和通用详情，不猜测用途。

### 4.3 小幅补充实际执行事件

保留旧 tool_started 的含义，增加 `ToolExecuting` / `tool_executing`，避免破坏现有消费者。

```json
{"event":"tool_executing","data":{"id":"call_123","name":"adjust_stock"}}
```

在参数校验通过、无需审批或审批通过之后，在第一次 handler 调用前发出。校验失败、未知工具、审批拒绝不发出此事件。内部重试不反复创建工具项；本阶段不提供单次重试进度。

共享事件类型、图节点、API 编码、前端协议和 trace/CLI 消费者同步检查。不能只在前端收到 tool_started 时人为改成“正在执行”。

### 4.4 有序内容模型

前端将每个用户请求及其后续助手消息视为一个展示轮次，用稳定 turn_id 关联，审批恢复与中断恢复继续更新同一轮次。

```typescript
type MessageBlock =
  | { id: string; type: "text"; step: number; text: string }
  | { id: string; type: "tool"; callId: string }
  | { id: string; type: "reasoning"; step: number; text: string };

type ToolStatus =
  | "prepared" | "waiting_approval" | "running"
  | "succeeded" | "failed" | "denied" | "unknown";
```

工具实体按 callId 保存，内容块只引用实体。相邻正文增量并入同一文本块；不同模型轮次或工具边界创建新块；工具完成更新已有实体，不在完成顺序处重新插入工具块。并行调用按请求顺序展示，完成状态独立更新。

reasoning 类型为阶段二预留，阶段一不生成思考内容。阶段状态作为轮次独立字段，不把计时刷新写入消息块。

旧快照以 user 消息为分组边界，将后续 assistant/tool 消息转换为有序内容块；缺少原始事件时只恢复能够确定的顺序，不补造耗时和审批过程。已完成历史消息不能因当前 busy 状态显示光标。

### 4.5 协议与异常处理

- 统一 SSE 解析，兼容网络分片、UTF-8 跨片段、LF/CRLF、多行 data 和注释心跳。
- 已知事件数据校验失败时显示可解释的协议错误；未知事件忽略并记录诊断，避免新增可选事件导致旧页面崩溃。
- 流结束必须区分正常 done、待审批状态与非预期 EOF；非预期结束不能静默变成完成。
- 心跳注释本阶段不作为业务进度。页面无新事件时显示“仍在等待响应”，不能仅凭计时判定后台已停止。
- 保留现有会话输入锁、冲突处理、显式恢复和审批防重复提交逻辑。

### 4.6 阶段一验收

1. 截图中的加粗和列表正常排版；表格、代码块、链接可读。
2. 浏览器收到发送动作后，下一个可见渲染帧出现占位状态，不等待正文首包。
3. 模型延迟 10 秒才返回正文时，状态和耗时持续可见；不出现虚构步骤。
4. 工具请求、审批等待、实际执行三种状态明确区分；批准前不显示“正在入库”。
5. 并行工具乱序完成时，各项正确配对；拒绝和业务错误不显示成功。
6. 用户向上阅读不会被新片段强制拉到底部；完成后的历史消息无运行光标。
7. 审批、中断恢复、冲突锁定行为继续通过现有回归检查。

## 5. 阶段二：思考增量、业务卡片与恢复一致性

### 5.1 思考能力与事件链路

智谱文档提供 thinking 配置和 reasoning_content 字段，但必须验证当前配置的模型、端点、SDK 与工具调用组合实际返回什么。使用一次受控、低成本真实请求检查字段和时序，常规测试继续使用脚本化模型。不得把“OpenAI 兼容”当作必然支持思考字段。

新增独立 `ReasoningDelta`，LLMClient 分别解析正文、思考、工具调用参数。思考不拼入 TextDelta，不写进 final_answer，不因展示需要额外调用模型。

链路：LLMClient → graph model writer → AgentEvent → API SSE → 前端 reasoning block。对应 trace、CLI 和测试客户端明确支持或忽略新事件。

```json
{"event":"reasoning_delta","data":{"step":1,"text":"供应商提供的思考片段"}}
```

思考区标题为“思考过程”，默认折叠，可展开实时阅读；轮次变化时分别保存。没有内容时显示阶段状态，不显示空思考面板。正文出现不自动删除用户正在阅读的思考内容。

思考展示作为配置能力，默认关闭，验证端点后再启用。阶段二默认仅保存在当前页面内存，不进入 messages、checkpoint、展示事件表或本地 trace；刷新提示“思考内容仅在本次连接展示”。持久化公开思考内容如有后续需求单独评审，不能无意扩大保存范围。

### 5.2 业务结果卡片

首批只实现三类明确契约：库存查询、库存调整、订单创建。其他工具显示通用结果详情；报价卡片等待真实工具契约确认，不凭模型输出推算。

采用后端展示适配器，把工具原始结果转换成版本化 display 字段，保留 content 供现有模型与消费者使用：

```json
{
  "id":"call_123",
  "name":"adjust_stock",
  "ok":true,
  "content":"原始工具结果",
  "display":{
    "version":1,
    "kind":"stock_adjustment",
    "outcome":"succeeded",
    "sku":"A1001",
    "delta":9,
    "quantity_after":9
  }
}
```

上例是拟定的展示协议，不是当前工具原始返回格式。适配器必须读取 MCP bridge/server 的实际返回契约：返回后的库存取自工具结果，调整量取自已验证的执行参数；不能从 AI 正文提取。调整成功说明本次操作的返回结果，不代表随后库存不会再被修改。

outcome 分类至少包含 succeeded、failed、denied、unknown。审批拒绝优先分类为 denied；transport ok、业务 error 字段、工具特定状态共同决定结果。无法确认的结果展示 unknown 和详情，不显示绿色成功卡。

适配器校验失败不影响已完成业务操作，也不重新执行工具；回退通用详情并记录诊断。前端对 display 再做版本和字段校验，未知 kind/version 回退详情。

工具结果到达即可显示卡片，不等待模型总结。AI 正文保留解释价值；可通过提示约定减少重复叙述，但禁止依靠正则删除任意正文中的业务数字。

### 5.3 展示持久化与刷新恢复

新增 RunStore 展示事件表，作为 UI 投影数据，不替代 LangGraph checkpoint，不参与写操作决策。

建议字段：session_id、run_id、segment_id、event_id、seq、type、payload、occurred_at、schema_version。run_id 表示用户请求所属运行；segment_id 表示一次初始/审批/中断恢复连接；seq 在运行内单调递增；event_id 用于客户端合并去重。

保存正文片段、模型阶段边界、工具请求/执行/结果和审批变化。正文按短时间窗口合并写入并保留文本块位置，节点结束、审批挂起、done/error 前强制刷新；计时刷新、连接心跳和原始思考片段不落库。正文增量日志保留到完成与恢复读取需要的范围，实施时设置明确清理策略，建议默认保留 30 天，历史 messages 仍可展示。

快照接口增加可选 presentation 字段，包含版本、轮次、blocks、工具展示数据、最后 seq、更新时间和 terminal 状态。旧客户端忽略该字段；新客户端优先使用，缺失时使用旧 messages 转换。现有 tool_history 恢复投影需补充实际已保存的 arguments，不能假定 API 当前已经返回参数。

恢复规则：

1. checkpoint 决定是否待审批、是否可继续和实际工具结果；展示日志只决定排版与可证明的过程。
2. 图节点提交和展示日志不在同一个事务内，必须处理缺失或落后投影：用 checkpoint 已保存的消息和结果校正展示，不重新执行业务。
3. 运行中的未提交文本可能因断连或崩溃丢失。页面标为“部分输出未保存”，不能宣称逐 token 恢复。
4. 事件按 event_id 去重、按 seq 合并；恢复段不新建重复工具卡；新用户请求创建新轮次。
5. 刷新时仍运行，复用现有状态轮询并返回 presentation，展示“正在同步状态”。本阶段不增加 SSE 断点续订、后台任务守护或浏览器断连后自动继续执行能力。
6. 非预期断连后先查询状态，再显示待审批、继续恢复或已完成；恢复执行仍走现有显式入口。不得自动重发原始写请求。
7. 旧会话没有运行关联信息时，按 user 消息边界恢复，不伪造 run_id、原始耗时或已丢失思考内容。

### 5.4 连接心跳

阶段二增加可选命名 heartbeat 事件，或把现有注释心跳纳入传输层观察。选择命名事件时由 SSE 传输包装层定时产生，不推进 graph step，不落展示日志：

```json
{"event":"heartbeat","data":{"at":"2026-10-07T02:00:00Z"}}
```

建议 10 秒间隔，30 秒无业务事件且无心跳时提示“连接暂未收到响应，正在检查状态”。这是一条连接提示，不能判定任务失败；判断仍以快照或执行错误为准。调度不得通过反复取消底层异步迭代来实现，以免取消模型或工具调用。

### 5.5 阶段二验收

1. 有思考字段时思考与正文分区实时显示；无字段或关闭功能时正常降级。
2. 思考字段不混入最终回答、模型 messages 与默认持久化日志。
3. 入库、库存查询、建单卡片的数据和 outcome 与工具实际结果一致。
4. transport ok 的业务错误、拒绝、未知结果均不显示业务成功。
5. 正常完成后刷新，正文与工具顺序一致，无重复正文或工具卡。
6. 审批挂起刷新、审批恢复、并行工具完成、执行中断恢复均保持关联。
7. 模拟 checkpoint 与展示日志不同步，恢复仍以 checkpoint 为准，不重复执行写入。
8. 心跳期间长时间无正文仍显示等待状态；心跳停止后显示连接提示而非伪造失败。

## 8. 验证方案

自动化重点覆盖行为契约，而非组件内部实现：

- 前端协议：任意分片、中文跨片段、多行 data、心跳、未知事件、非法数据、非预期 EOF。
- 状态 reducer：文本/工具交错、并行乱序、恢复段去重、审批拒绝、业务错误、max_steps 收口。
- 后端事件：执行事件必须晚于批准且早于实际 handler；拒绝或校验失败不执行。
- 展示适配器：成功、业务 error、拒绝、未知格式；金额以工具契约为准，不通过浮点数重新计算。
- 持久化：旧表兼容、日志缺失校正、恢复不重放业务、已完成会话顺序一致。

复用 `apps/web` 的现有测试命令和构建、相关 API/agent_core pytest。组件引入后根据测试需要调整编译入口。只有行为测试需要时才增加 DOM 测试依赖。

浏览器验证使用脚本化模型构造 10 秒无正文、并行工具、批准/拒绝、错误、连接中断、刷新恢复；检查控制台、网络首包与事件时序。截图覆盖桌面与窄屏、Markdown 表格、展开详情、用户向上阅读。真实模型调用只用于供应商能力验证，不作为常规测试前提。

关键证据：首个占位状态出现时间、首个服务端事件时间、工具批准/实际执行时序、最终业务结果、刷新后的内容顺序。以浏览器观察验证是否存在代理缓冲，不把 CSS 动画当作真实流式证据。

## 9. 已知边界

- 公开思考内容能否实时获得取决于供应商；无思考字段不影响阶段一体验。
- 当前 checkpoint 按节点保存，不能保证正在生成的每个 token 都可恢复。
- 展示日志与 checkpoint 非原子提交，需要校正，不能把 UI 记录当作业务账本。
- 本方案不实现完整崩溃对账、自动续跑、多进程调度或 SSE 历史订阅；现有 ADR-0008/0009 的边界继续适用。
- 工具重试内部细节暂不逐次展示；等待期间显示执行状态和耗时，不虚构子步骤。
- 全链路事件扩展需要兼容 trace、CLI、脚本化模型与旧会话，不能仅修改前端类型。
