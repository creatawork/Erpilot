## 1. 现状事实（实现契约的出发点）

| 代码事实 | 位置 | 对契约的约束 |
|---|---|---|
| 审批等待 = `asyncio.Future` + resume 闭包，内存 waiter 字典 | `agent_core/approval.py` StreamApprovalGate | 恢复必须从数据重建 waiter；pending_id 可保留原值（uuid hex 12 位） |
| `client_token` 在写 handler 首次执行时生成 | `mcp_erp/bridge.py`（`args.client_token = uuid4().hex`） | token 生成点必须前移到审批展示前，由 run_store 持久化后注入 |
| 会话历史与每会话锁在内存，未完成轮回退 | `erpilot_api/service.py` | 历史回退 ≠ 撤销业务；恢复以 invocation 记录为准 |
| 事件协议有 approval_pending/resolved，无持久化查询与游标 | `erpilot_api/events.py` | 新增 (run_id, seq) 单调事件表与补发接口 |
| 业务幂等：`MutationRequestRow`（token → request+result，同事务） | `erp_store/mutations.py` | "是否成功提交"只认这张表；运行表不做第二事实源 |

## 2. 数据契约（run_store 五表）

实现于 `apps/api/src/erpilot_api/run_store.py`（SQLite；建议独立文件
`data/runs.db`，不与业务库混用文件；均可用临时文件库测试）。

### run_session
| 字段 | 说明/约束 |
|---|---|
| session_id | PK |
| schema_version | 运行模型版本；不支持的版本拒绝恢复写入 |
| active_run_id | 可空；活动 run 引用 |
| history_json | 已完成轮次的完整模型消息历史；仅在 run 完成时更新 |
| created_at / updated_at | UTC |

约束：一个会话最多一个活动 run——由 run 表的部分唯一索引承载（见下），
本表 active_run_id 是冗余读路径，以 run 表为准。

### run
| 字段 | 说明/约束 |
|---|---|
| run_id | PK（uuid4 hex） |
| session_id | FK → run_session |
| user_input | 原用户消息（重放对话区用） |
| status | running / waiting_approval / recovering / completed / failed / cancelled |
| checkpoint_version | 检查点格式版本（int，随协议演进递增） |
| final_answer / error | 可空；收口时写 |
| messages_json | 本轮最近一个安全检查点的完整模型消息（含工具调用组及全部已决结果）；半组消息不得用于续段 |
| execution_owner / lease_until / revision | 可空执行者标识、UTC 租约到期时间、CAS 版本；同一 run 的并发 resume 只能有一个执行者 |
| trace_path | 关联 JSONL trace（证据，不是可执行命令源） |
| created_at / updated_at | UTC |

约束：**部分唯一索引** `(session_id)` WHERE status IN
('running','waiting_approval','recovering') —— 同会话至多一个活动 run，
重复创建由该约束拒绝；同一 run 的重复 resume 另由 execution_owner、
lease_until 和 revision 的条件更新裁决，活动 run 唯一索引不能充当执行锁。

### invocation
| 字段 | 说明/约束 |
|---|---|
| invocation_id | PK |
| run_id | FK → run |
| call_id | 模型侧工具调用 id（ToolCallStarted 的 id） |
| tool | 工具名 |
| tool_schema_version | 参数 JSON Schema 的 sha256（MCP inputSchema） |
| arguments_json | 规范化参数（同 mutations `_request_json` 口径：`json.dumps(..., sort_keys=True, ensure_ascii=False)`） |
| arguments_fingerprint | sha256(tool + tool_schema_version + arguments_json) |
| client_token | 服务端生成；**全局唯一**（唯一索引） |
| approval_pending_id | 可空 FK |
| status | prepared / waiting_approval / approved / executing / succeeded / denied / failed / unknown |
| result_json | 可空；成功/拒绝/失败的结构化结果（回填模型用） |
| updated_at | UTC |

### approval
| 字段 | 说明/约束 |
|---|---|
| pending_id | PK（沿用 gate 的 uuid hex 12 位生成规则） |
| invocation_id | FK，UNIQUE（一调用一审批） |
| run_id / session_id | 冗余归属，恢复时做一致性检查 |
| arguments_fingerprint | 绑定原参数——批准不可迁移到异参动作 |
| status | pending / approved / denied / expired / cancelled |
| expected_version | 乐观锁版本号（决策条件更新用） |
| decided_reason / decided_at | 决策留痕 |
| expires_at | UTC；默认 created_at + TTL（30 分钟，env `ERPILOT_APPROVAL_TTL_SECONDS` 可配） |
| created_at | UTC |

约束：只能从 pending 决策一次——决策用条件更新
`UPDATE approval SET status=:s, ... WHERE pending_id=:p AND status='pending'
AND expected_version=:v`，rowsAffected=0 即竞争失败（R07）。

### run_event
| 字段 | 说明/约束 |
|---|---|
| run_id + seq | 复合唯一（seq 每 run 单调递增，从 1 起） |
| event_type | 复用 SSE 事件名 + 少量内部事件（run_status_changed 等） |
| payload_json | 与 events.py 编码同构 |
| created_at | UTC |

保留策略（首版冻结）：run_event 与 run 全量保留、**显式不清理**；业务幂等
表照旧永不自动删除。清理策略推迟到有真实数据量后另立 ADR。

### 初始化与升级
- 非破坏性初始化：建表用 `checkfirst`，已有库按 `schema_version` 校验；
  不支持的旧版本**拒绝恢复写入、保留原数据**，不通过 re-seed 升级。
- 已有业务数据库无需任何变更即可共存（两库互不感知）。

## 3. 状态机与窗口

run：`running → waiting_approval → recovering → completed/failed/cancelled`
（waiting_approval 与 running 可随并行调用交错；recovering 仅恢复执行者持有）。

invocation：`prepared → waiting_approval → approved → executing → succeeded /
failed / unknown`；`prepared → denied`（门拒）；任何非终态可由恢复进程改写。

**落盘与业务提交的窗口枚举**（每个写调用的生命周期；恢复行为按窗口定义）：

| 窗口 | 已持久化 | 未持久化/未知 | 恢复行为 |
|---|---|---|---|
| W1 prepared（token 与审批已落盘，尚未展示） | invocation + token + approval(pending) 在同一运行库事务提交 | 展示事件 | 重建同一 pending_id 展示；未经批准不得执行（R01） |
| W2 waiting_approval | + approval_pending 展示事件（approval 在 W1 已落盘，原 expires_at 不变） | 决策 | 保留原 TTL 重挂；过期只能新建审批（R02） |
| W3 approved | + approval(approved) | 执行 | 核验指纹+版本后用原 token 执行一次（R03） |
| W4 executing | invocation.status=executing | 业务事务是否提交 | 先按 token 查幂等表对账（R04/R05） |
| W5 committed | 业务幂等行已有 | result_json | 取回首次成功结果回填（R05） |
| W6 result 落盘，回答未生成 | + result_json | final_answer | 从工具结果重新生成回答，不重放写调用（R06） |

unknown 的定义与出路：token 对账查询本身失败（DB 错/超时）→ status=unknown，
前端显示"结果待核对"，**禁止换 token 重跑**；查询成功且无幂等行 → 事务未提交，
仅当原批准有效、指纹一致、工具满足事务幂等契约（ADR-0007 四工具均满足）时
允许**原 token** 重试一次；仍失败则 unknown。无记录不单独证明未执行——
该条件只在查询成功的前提下成立。

## 4. API 契约（冻结稿；T04–T08 按此实施）

兼容：`POST /api/chat/stream` 与 `POST /api/chat/approve` 保留现语义；
approve 请求体新增可选 `run_id`、`expected_version` 字段，缺省时行为与旧
客户端一致（pending_id 仍必填）。错误语义不静默变更。

| 端点 | 语义 | 错误码 |
|---|---|---|
| GET /api/runs/{run_id} | 快照：run 状态、逐 invocation 结果、待审批列表（含 expected_version/expires_at）、final_answer、last_seq | 404 |
| GET /api/sessions/{session_id}/runs | 会话的任务列表（活动 + 最近），页面刷新找回 | 404 |
| GET /api/runs/{run_id}/events?after_seq= | 先查快照再补事件（见 §5 交界协议） | 404 |
| POST /api/runs/{run_id}/resume | 幂等提交恢复；已有活动执行者时返回当前状态 200（不第二个执行者） | 404 / 409（schema 或指纹不兼容） |
| POST /api/runs/{run_id}/cancel | 显式取消：关闭未决审批（cancelled）、未开始调用停止、已执行按 token 对账 | 404 |
| POST /api/chat/approve | 决策回填；同决定重复 → 200+原结果；相反决定/版本冲突 → 409（body 带当前决定）；过期 → 410；未知 pending_id → 404 | 404/409/410 |

订阅断开 vs 显式取消：SSE 连接断开只终止订阅（服务端 run 继续、事件照落
run_event）；`/cancel` 是唯一把 run 置为 cancelled 的入口。AnyIO 取消回归
测试相应区分两条路径。

## 5. 快照与事件流交界（R10）

客户端连接顺序：`GET /api/runs/{run_id}` 取快照（含 last_seq）→ 以
`after_seq=last_seq` 订阅事件 → 服务端在生成快照后、订阅建立前排队的补发
事件允许重复到达，客户端按 `(run_id, seq)` 去重。无缺口的要求由
"快照 ≥ 订阅起点" 保证：快照覆盖到 last_seq，订阅只补 last_seq 之后。
回答区以快照 final_answer 重置，增量 delta 只在订阅后追加——避免文本
重复拼接。多待审批各自独立 pending_id 与 call_id 配对。

## 7. 桌面推演记录（R01–R10，2026-10-05）

逐场景按 §2/§3 契约推演，三个重点路径结论如下；全部场景成立，未发现
需要修订规划的安全恢复路径。

**推演 1 —— 多调用一半完成**（并行组 A 成功、B 待审批、C 未开始）：
run 状态 waiting_approval；A 的 invocation=succeeded 且 result_json 已落
（W5 完成），B=waiting_approval（W2），C=prepared（W1）。恢复时：A 不再
执行——回答重建直接从 result_json 取工具结果回填消息历史；B 按原 pending_id
重挂 waiter 等 decision；C 保持 prepared，待模型续段时按原计划执行（执行前
仍过门）。检查点保证每步的工具调用组完整：已决调用带结果、未决调用带
invocation 引用，模型消息协议在恢复前校验（缺 tool result 的半组历史
不允许进入续段）。

**推演 2 —— 同意/拒绝竞争 + 重复点击**：两个并发决策到达 → 条件更新
只有一个 rowsAffected=1：胜者生效并产生 approval_resolved 事件；败者 409，
body 返回已生效决定（前端把卡片刷新为最终状态而非报错炸掉）。重复同决定
在已决后到达 → 幂等 200 返回原结果，不产生第二个事件。expected_version
随每次展示快照递增，旧页面持过期版本提交 → 409 同路径处理。

**推演 3 —— 查不到 token**：恢复时按 client_token 查业务幂等表分三种：
(a) 查询失败 → invocation=unknown，展示"结果待核对"，禁止任何重试（R09）；
(b) 查询成功、有行 → 校验 request 与指纹一致后取回结果回填（W5），不一致
即 idempotency_conflict，终止该恢复路径并明确提示重新发起（R09 的异参
分支，原批准不迁移）；(c) 查询成功、无行 → 事务未提交，按 §3 unknown 规则
判定是否原 token 重试一次（仅批准有效+指纹一致+幂等契约满足）。

其余：R01（W1 重启→同 pending 找回、业务零变化——尚未到业务层）、
R02（TTL 以 expires_at 绝对时间判定，重连/重启不重置）、R04（提交前硬终止
→ SQLite 事务回滚，无半笔数据）、R06（W6 只重生成回答，工具结果来自
result_json）、R07/R08（§4 条件更新 + run 活动唯一索引裁决执行权）、
R10（§5 交界协议）——均在既有契约内闭合。
