# ADR-0008：运行持久化与断点恢复（run store 数据化检查点）

- 状态：草拟（待技术负责人评审后接受，检查点 C1）
- 日期：2026-10-05
- 关联：[下一阶段总体规划](../../tasks/plan.md) §4（设计建议来源）、[恢复协议明细](../plans/恢复协议明细.md)（冻结明细）、ADR-0005/0006/0007

## 背景

M4 交付了写入可靠性（事务幂等 + 并发保护，ADR-0007）与挂起式审批事件
（ADR-0006），但运行状态仍全部在内存：ChatService 的会话/锁是内存字典，
StreamApprovalGate 的等待由 Future + resume 闭包承载，写调用的 client_token
在 handler 执行时才生成（bridge.py），事件协议没有持久化 run 查询与游标。
用户刷新页面、断连或 API 进程重启后，本轮任务、待审批事项、已执行结果
全部丢失；更严重的是"已批准未执行""已提交未知结果"这类窗口无法对账。

约束：本机单用户、单执行进程、手写 loop（不引入 LangGraph/PostgreSQL，
迁移是后续独立决策）；agent_core 保持零业务依赖；不自动补偿或撤销业务；
已有业务四表与幂等表（MutationRequestRow）是"是否成功提交"的唯一依据。

## 决策

1. **应用层自持运行存储**：新增 `apps/api/src/erpilot_api/run_store.py`，
   SQLite 建模 session / run / invocation / approval / run_event 五张表
   （字段与唯一约束见恢复协议明细），与业务库的幂等表分开建模，互不假设
   同库同事务；两者以 client_token 对账衔接。
   session 保存已完成消息历史，run 保存完整安全检查点；同一 run 的恢复执行权
   由租约与版本条件更新裁决，活动 run 唯一索引只约束新 run 创建。
2. **数据化检查点，不序列化执行体**：落盘的是可重建的调用数据（规范化参数、
   参数指纹、token、审批关联、结构化结果），恢复 = 从数据重建待审批与续段，
   不保存也不反序列化 Future / 闭包 / 协程。
3. **token 纪律**：服务端在**首次展示审批前**生成并持久化 client_token；
   同一 invocation 的任何重试复用原 token；恢复路径禁止重新生成。
   业务幂等表是提交事实的唯一来源，运行表是"下一步可以做什么"的依据。
4. **状态机分离**：run 状态（running / waiting_approval / recovering /
   completed / failed / cancelled）不代替 invocation 状态（prepared /
   waiting_approval / approved / executing / succeeded / denied / failed /
   unknown）；一个 run 内多个调用的结果逐条落盘、逐条恢复。
5. **审批决定持久化一次**：决策以条件更新落盘（仅 pending 可决），重复
   同决定幂等返回原结果，相反决定 409，过期 410；pending TTL 默认 30 分钟
   （可配置、UTC 存储、测试注入时钟），断连与重启不延长。
6. **订阅与执行分离**：SSE 断开只终止订阅；显式 cancel 才关闭未决审批并
   停止未开始调用；已提交结果按 token 对账，绝不宣称"必然未执行"。

## 理由

- **为什么不序列化 Future/闭包**：跨进程不可恢复、绑定事件循环与栈帧，
  且把"恢复"退化成"重放整个 run"——重放会二次执行已批准的写调用。
  数据化检查点是唯一能支撑"审批前重启找回原审批、提交后重启核对原结果"
  演示（tasks/plan.md §1）的结构。
- **为什么自持 run store 而非复用业务幂等表**：幂等表回答"该 token 是否
  成功提交、结果是什么"，不回答"run 走到哪一步、哪些调用还欠审批/欠回答"。
  混用会让两个生命周期互相绑架（清理、schema 演进、并发度都不同）。
- **为什么不现在引入 LangGraph checkpointer**：恢复语义的正确边界（窗口
  枚举、unknown 处理、审批一致性）是框架无关的领域问题，先在手写 loop 上
  定义并验收（R01–R10），迁移时这份契约会变成对 checkpointer 的需求清单。
  过早引入会用框架语义掩盖未想清楚的恢复边界（风险表第 8 条的退出条件）。
- 备选"只持久化最终结果、中间态靠重放"被否：重放违背"同一次已批准写调用
  最多一次业务变更"的阶段目标。

## 后果

- API 进程重启后：待审批可找回（同 pending_id、原 TTL）、已批准可按原
  token 执行一次、已提交可对账、回答可从持久化工具结果重新生成。
- 代价：五个新表与状态机的维护成本；写路径每个窗口都要先落盘再动作，
  延迟增加一次本地 SQLite 写（本机量级可忽略）。
- 首版显式不清理 run_store 记录；schema 不兼容时拒绝恢复并保留原数据。
- 单执行进程是硬边界：并发 resume 用数据库条件更新裁决执行权（R08），
  不做跨进程调度。
- 验收阈值（冻结）：R01–R10 全过是本阶段完成线；真实模型回归视图保留
  原 35 条范围，通过 ≥34 且无新增未归因退化，edge-08 按 v2 口径单列，
  新增恢复集单独统计；未批准写入 / 重复业务写入 / 执行失败宣称成功
  零容忍（详见恢复协议明细 §6）。
