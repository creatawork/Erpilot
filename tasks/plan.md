# Erpilot 下一阶段规划：M4 验收补缺与持久化恢复

- 编制日期：2026-10-05。
- 状态：规划草案，供后续开发交接；本次仅编写文档，未实施下列功能。
- 任务清单：[todo.md](todo.md)；长期路线：[启动计划](../docs/agent-project-plan.md)。
- 阶段定位：承接 M4 写入可靠性成果，为 M6 编排迁移准备恢复验收集；不因月份编号直接启动框架迁移。

## 1. 下一阶段要交付什么

在单用户、本机、单 API 进程的范围内，让用户关闭页面或重启服务后，仍能找到本轮任务、待审批事项及已执行结果；同一次已批准写调用最多产生一次业务变更。先完成 M4 未闭环的行为验收，再以库存调整为第一条恢复链路，逐步覆盖全部四个写工具。

阶段演示应能展示：发起入库 → 待审批时重启 → 找回原审批 → 批准 → 在业务提交后中断 → 重启核对原结果 → 显示库存仅增加一次。另一条拒绝路径必须证明业务表无变化。

### 4.1 存储与职责

优先保留手写 loop 与 SQLite，新增由应用持有的运行存储模块（建议 apps/api/src/erpilot_api/run_store.py）。与现有业务幂等表分开建模；不要求运行状态与业务变更跨库原子提交，以 token 对账处理两者的提交间隙。若同文件部署，也不得把应用运行模型塞进 agent_core。

| 记录 | 最小字段/约束 |
|---|---|
| session | session_id、已完成轮次历史、活动 run_id、schema_version；同会话最多一个活动 run |
| run | run_id、session_id、用户输入、状态、checkpoint_version、创建/更新时间、最终答复、错误、trace 关联 |
| invocation | invocation_id、run_id、模型 call_id、工具名、规范化参数、参数指纹、client_token、审批关联、执行状态、结构化结果；token 唯一 |
| approval | pending_id、invocation_id、参数指纹、状态、expires_at、决定/原因/时间、版本号；只能从 pending 决策一次 |
| event | run_id、单调 seq、事件类型、载荷、时间；(run_id, seq) 唯一，用于重放与去重 |

写调用和 token 先落盘，再展示审批，再按持久化的决策执行。审批摘要绑定具体参数，用户批准后模型不能替换参数。业务幂等记录是“是否成功提交”的依据；运行记录是“下一步可以做什么”的依据，trace 是证据，不是可执行命令源。

新增表采用非破坏性初始化与版本检查，不通过重新 seed 升级旧库。不自动删除仍可能用于恢复的幂等结果；保留与清理策略在 T03 记录，首版可显式不清理。旧版本遇到不支持的运行 schema 应拒绝恢复写入，保留原数据。

### 4.2 状态与恢复语义

run 建议状态：running、waiting_approval、recovering、completed、failed、cancelled。invocation 单独记录 prepared、waiting_approval、approved、executing、succeeded、denied、failed、unknown。一个 run 可能含多个调用，不得用 run 状态代替每次调用结果。

| 中断点/动作 | 必须遵循的行为 |
|---|---|
| 调用已记录，审批尚未展示 | 恢复同一 pending_id；未经批准不得执行 |
| 等待审批时断连或重启 | 保留待审批记录与原到期时间；重连不延长 TTL；超过期限只能新建审批 |
| 已批准但尚未执行 | 核验版本与参数指纹，使用原 token 执行一次 |
| 已开始执行，提交结果不明 | 先按 token 查询业务结果；找到则回填；查询失败显示 unknown，禁止换 token 重跑 |
| 查询成功且未找到记录 | 只有原批准有效、参数未变且工具满足事务幂等契约，才可使用原 token 重试；没有记录不单独证明未执行 |
| 业务已提交，运行记录/回答未完成 | 取回首次成功结果，修复运行记录；恢复回答阶段不得重新规划或重放已完成写调用 |
| 模型回答过程中中断 | 允许从已持久化工具结果重新生成回答；不承诺逐 token 原样续写，不重复写业务 |
| 用户拒绝/审批过期 | 记录未执行结果；禁止被迟到批准覆盖；业务四表不变 |
| 用户显式取消 | 关闭未决审批；未开始调用停止；已执行/执行中按 token 对账，不宣称撤销或必然未执行 |
| 参数或工具版本变化 | 原批准不可迁移到新动作；终止该恢复路径，明确提示重新发起并审批 |

建议 pending TTL 为 30 分钟（可配置，按 UTC 存储，测试注入时钟）；TTL 只控制尚未决定的审批，已落盘批准的执行遵循上表。审批归属绑定 run/session 是一致性检查，不等于身份认证，当前边界仍为可信本机单用户。

SSE 订阅断开与用户取消分开：断连只停止订阅，服务端执行可继续并落盘；等待审批的任务保持等待。首版只支持单执行进程，仍需数据库版本检查防止同一 run 在并发请求中恢复两次。进程重启从安全检查点恢复，不重放整轮用户请求。

### 4.3 接口与前端交付契约（拟议，非已存在接口）

- 保留当前 POST /api/chat/stream 与 POST /api/chat/approve 的兼容路径；新恢复能力使用显式版本或可识别的新字段，不静默改变旧客户端错误语义。
- 拟增 GET /api/runs/{run_id}：任务状态、调用结果、待审批列表、最终答复、last_seq。拟增 GET /api/sessions/{session_id}/runs：页面刷新后找回活动与最近任务。
- 拟增 GET /api/runs/{run_id}/events?after_seq=…：补发持久化事件并跟随实时流；明确先订阅/快照的竞争处理，保证无事件缺口。
- 拟增 POST /api/runs/{run_id}/resume 与 /cancel：恢复既有任务或显式取消；幂等提交，活动执行存在时返回当前状态。
- 审批请求带 run_id、pending_id、expected_version；相同决定重复提交返回已决结果，相反决定/版本冲突返回 409，未知 404，已过期 410。最终字段及旧入口映射在 T03 冻结。
- 页面以服务端快照为准，按 (run_id, seq) 去重；刷新恢复审批卡，不重新发送原聊天消息。显示“业务已执行，回答待恢复”“结果待核对”“审批已过期”等实际状态。
- 持久化最终答案和关键业务事件；流式 delta 的保留粒度由 T03 定义。首版可不保存每个 delta，但重连必须用快照重置回答区，避免文本重复拼接。

## 6. 验收矩阵与证据要求

以下是未来必须执行的验证，不代表已通过。R01–R10 为确定性工程门槛，任何失败均阻止本阶段完成。

| ID | 故障/操作 | 断言与证据 |
|---|---|---|
| R01 | 持久化待审批后、展示前重启 | 同一调用/审批可找回，无业务变化 |
| R02 | 待审批时刷新、断网、重启 | 原审批仍可决定且 TTL 不延长；过期不能执行 |

| R05 | 提交成功、响应返回前强制终止 | 成功结果可查询，业务不重复变更 |
| R06 | 结果落盘后、最终回答前重启 | 回答来源可追溯，不再调用已完成写工具 |

| R08 | 同 run 并发恢复/取消 | 至多一个执行所有者；已提交结果不会被标成未执行 |
| R09 | 查询失败、同 token 异参、旧 schema/工具版本 | 阻止盲目写重试，保留状态与诊断信息 |
| R10 | 快照与事件订阅交界断连、重复事件、多待审批 | 无事件丢失或重复卡片；每个 call_id 结果正确配对 |
| B01 | insufficient_stock / invalid_transition | 真实模型解释错误并作允许的只读复核；不能为恢复而擅自改写业务条件 |
| B02 | 真人批准与拒绝 | 模型真实、审批人工、临时库隔离；保存审批决定、调用结果及业务前后值 |
| B03 | 校准后的完整评测 | 全范围执行，失败逐条归因；报告明确范围和判分版本，不与旧 35 条直接混比 |

R01–R06 至少对 adjust_stock 做完整垂直验证；T10 将四个写工具的关键提交窗口 R03–R06 参数化覆盖，并保留跨调用序列及同轮多审批用例。硬终止必须用独立子进程测试，不能只用抛异常冒充进程崩溃。所有破坏性故障测试使用临时数据库。

每份验收记录包含：代码 revision/源码哈希、场景/判分版本、固定 seed、run_id/pending_id/token 关联、审批决定、故障注入点、业务表前后快照、执行次数、trace 路径、耗时和失败原因。模型报告额外记录调用次数、预算、实际返回 usage、估算成本与缺失计量。

真实模型阶段建议阈值：保留原有 35 条范围做回归视图，通过不少于 34 条且无新增未归因退化；edge-08 按新口径单列。新增恢复集单独统计。未经批准写入、重复业务写入、执行失败却宣称成功均零容忍。该阈值是本规划建议，T03 冻结；评分口径变更后必须重跑，不改写旧报告。

## 8. 风险与后续决策

| 风险 | 处理与退出条件 |
|---|---|
| Future/闭包无法跨进程恢复 | 数据化检查点与受限恢复入口先验收；若无法在不重跑写入的前提下续行，停在 T03 复核，不堆补丁 |
| 执行日志与业务事务提交不一致 | 写前持久化 token、写后按 token 对账；unknown 明确展示，禁止新 token 重试 |
| 参数规范化口径不一致 | 与现有 mutation 指纹定义保持一致，验证同参数/异参数正反例 |
| 历史消息中残留缺失 tool result | 检查点包含完整工具调用组及结果；恢复前验证模型消息协议 |
| 当前 SSE 取消会清理审批 | 新协议显式区分订阅断连/用户取消；旧行为兼容测试随协议更新 |
| 缺少身份认证 | 维持本机展示范围；run/session 绑定不能作为对外访问控制 |
| 真实评测受模型波动影响 | 确定性恢复测试与模型行为分开报告，保存失败，不为通过率放宽检查 |
| 手写恢复复杂度持续增长 | 在同一恢复验收集上评估 LangGraph/PostgreSQL，再写迁移 ADR；本阶段不预先引入 |

下一阶段之后才安排：身份认证、审批归属到具体用户、审计与数据保留、部署及备份恢复演练。该扩展与当前启动计划“不做登录/多用户”冲突，必须先通过范围 ADR 更新，再实施对外写入部署。公开部署不是本阶段交付承诺。
