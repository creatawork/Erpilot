# ADR-0005：写操作分层进工具面，审批门内建于工具层

- 状态：已接受
- 日期：2026-10-05

## 背景

M3 收口时工具面是纯只读的——repository 刻意不提供写入口（repository.py 模块
注释即决策记录），系统提示词也声明"工具面没有写操作"。M4 要把工具面扩到
可写：建订单、改库存、取消订单、上下架商品。写操作是新风险面：模型一旦能
动账动货，"幻觉执行"（没执行却说执行了）和"顺从越权指令"（adv-04 考的
场景）就从无害的嘴误升级成真实的业务事故。

方案空间：

1. **提示词约束**：继续不让模型碰写工具，用户要求写操作时口头拒绝；
2. **写工具直连**：写操作上工具面，靠系统提示词要求"先征得用户同意"；
3. **审批门（本 ADR）**：写工具上工具面，但执行被代码层拦截，经审批才放行。

计划 §4 早已冻结 HITL 分级口径：只读放行 / 低风险批量确认 / 资金操作单笔
确认。M6 的 LangGraph interrupt + checkpointer 是这个口径的工业级实现；
在引入框架之前，先手写一遍才能理解 interrupt 到底在解决什么问题（ADR-0002
"先懂机制再用框架"的既定策略在 HITL 上的延续）。

## 决策

1. **写 API 与读 API 分层**：写操作进独立的 `erp_store.mutations` 模块
   （`ErpMutations`），不进 `ErpRepository`——读入口保持只读语义，写入口
   显式、可枚举、可审计。写路径的领域规则在这里执行：
   - `create_order`：商品须在售、库存须足量，**快照价取现价 + 库存扣减同
     事务提交**（下单快照价语义从 M3 只读侧延伸到写侧）；
   - `cancel_order`：状态机约束（仅待付款/待发货可取消），取消回补库存；
   - `adjust_stock`：库存不为负；`set_product_status`：幂等目标状态直接成功
     ？不——目标状态与现状一致返回 `invalid_transition`（"无需变更"），
     让模型如实转述而不是把空操作报成成功。
2. **风险分级挂在工具上**：`Tool.risk: str | None`——`None` 即只读放行；
   `batch_confirm`（低风险，如 adjust_stock / set_product_status）与
   `single_confirm`（资金/单据，如 create_order / cancel_order）两级先落
   枚举值，分级消费策略在 M4 第 2–3 周的审批流里兑现。
3. **审批门内建于工具层**：`agent_core.approval.guarded(tool, gate)` 返回
   同名同 schema 的包装工具，handler 先 `gate.review(...)` 再决定执行或回填
   结构化"未执行"结果。**门在工具层内**，agent loop 与组合层零改动——
   提示词是软约束，门是硬约束：模型无论如何被诱导，代码不执行就是不执行。
4. **无 gate 不给写工具**：`build_agent_tools(writes=True)` 不传
   `approval_gate` 直接 raise——写工具不过审批门就不该存在，这是结构性
   保证而不是调用约定。默认 `writes=False`，现有 16 个只读工具面不变。
5. **错误契约 v1 延伸到写路径**：新增 `invalid_transition`（状态机非法迁移）
   与 `insufficient_stock` 两个 code，hint 一样给可操作的下一步；mutations
   抛 `MutationError`，MCP 工具层转成 `{"error": {code, message, hint}}`。
6. **评测环境无真人，审批门以 AutoDenyGate 参评**：拒绝一切写调用，考的
   是"未批准不得假装执行、如实转述"——这是写操作上线第一周唯一能程序化
   复核的行为口径；真实写链路的行为评测等第 3 周脚本化审批策略参评后再收。

## 理由

- 方案 1（纯提示词）与 M4 的存在理由冲突：写操作不进工具面，HITL 三深方向
  就没有实证场。方案 2 把治理交给提示词，恰恰是 adv 系列评测反复证明不可靠
  的层（adv-05 的教训：诱导之下模型会顺从）。方案 3 让"是否执行"脱离模型
  的裁量权，模型保留"发起请求 + 转述结果"的职责。
- 门放工具层而非 loop 层：loop 是通用机制（不读业务语义），工具自带风险
  等级、由组合层在装配时包门，依赖方向干净（agent_core 不知道 ERP 的存在）；
  也让第 2 周把 review 从同步回调升级为待审批事件时，只改 gate 实现。
- `set_product_status` 对"已是目标状态"返回错误而非成功：写操作的返回值
  会被模型当作战果转述给用户，空操作报成功是在训练模型说谎——与 M3
  "工具永不假装"的整体口径一致。
- AutoDeny 参评而非 AutoApprove：评测库虽是临时库，但"批了就真写"的评测
  case 考的是执行正确性（第 3 周用脚本化审批做），第一周考的是治理行为，
  两者混在一起会让失败归因含糊。

## 后果

- 写工具的描述里必须自带"需审批"语义（进 inputSchema），模型在调用前就有
  预期，拒绝后不意外；
- 系统提示词从"没有写操作"改为"写操作需审批"的条件化文案
  （`system_prompt(writes_enabled)`），读工具面的既有评测口径不变；
- 审批门的同步 review 是原型形态：真人审批意味着会话挂起，那需要第 2 周
  的待审批事件与会话持久化，本 ADR 只冻结"门在工具层 + 无 gate 无写工具"
  两条不变量；
- 幂等键（重复提交返回原单）明确推迟到第 3 周——先让写路径跑通，再处理
  并发与重复语义。
